## Domain glossary

### Tenant (Org) and roles (M1)
**What it is:** a trade contractor company (HVAC is the first trade built; plumbing and electrical follow) that subscribes to the app. The schema is shared, every row carries an `org_id`, and Postgres RLS enforces isolation. Members have one role: owner, admin, estimator or viewer. Login is by magic link.
**What we built:** tables `orgs` and `memberships` (one role per user per org, `unique (org_id, user_id)`) in [supabase/migrations/20261019174738_init.sql](supabase/migrations/20261019174738_init.sql), on the Supabase project `service-agreement` (ref `gnxebrtcpbujhvcamtoe`, region `ca-central-1`).
- **Isolation:** every tenant table has `org_id not null`, and child rows reference parents through `(id, org_id)` composite foreign keys, so a reference cannot cross orgs (AD-003).
- **RLS:** enabled on all 16 `public` tables. Policies call `private.is_org_member(org)` and `private.has_org_role(org, roles[])`, which are security definer with an empty `search_path`, in a `private` schema the Data API does not expose (AD-004).
- **Who writes what:** members read everything in their org except `outbox`. Owner and admin write settings and the equipment catalog; memberships and invitations are written only by the member functions below (members-page), never directly. Owner, admin and estimator write customers, contacts, sites, assets, agreements, versions, service lines, contracts and events. Viewers only read. `anon` can read no rows and write nothing.
- **Sign-in (staff):** a **sign-in link** by email, not a password. Customers get a different **portal link** (M9), with no account.
  - `/login` ([web/app/login/](web/app/login/)) asks Supabase for a link with `shouldCreateUser: false`, so only existing users get one. An unknown address sees the same "Check your email" answer and gets no account (Supabase answers 422 `otp_disabled`).
  - The email links to `GET /auth/confirm?token_hash=…&type=email` ([web/app/auth/confirm/route.ts](web/app/auth/confirm/route.ts)), which calls `verifyOtp`, sets the session cookies and redirects to `/pipeline`. A missing, wrong, used or expired link redirects to `/login?error=link_invalid` (Supabase answers 403 `otp_expired`). Both redirects go to the public origin from `publicOrigin` ([web/lib/public-origin.ts](web/lib/public-origin.ts): `APP_BASE_URL`, then `x-forwarded-host`/`x-forwarded-proto`, then the request URL), because behind Railway the request URL is the container's `localhost:8080`.
  - **Supabase config outside the repo:** the Magic link email template's link must be `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`, and the Site URL `http://localhost:3000` in dev. Supabase only allows editing the templates with custom SMTP, so the project sends through Resend (`smtp.resend.com`); until a domain is verified there, it delivers only to the Resend account's own address.
  - **Session refresh:** [web/proxy.ts](web/proxy.ts) runs `updateSession` ([web/infrastructure/supabase/session.ts](web/infrastructure/supabase/session.ts)) on every request except build assets and images. `getClaims()` refreshes an expired token and the new cookies go on the response. Signed out, any path except `/login` and `/auth/confirm` redirects to `/login`; signed in, `/login` redirects to `/pipeline`.
  - **Who is signed in:** `currentMember()` from `getContainer()` returns `signed_out`, `no_membership` or `member` (user, email, org, org name, role). Identity comes from `getClaims` (`sub`), never `getSession`. `getContainer()` first awaits `connection()`, so the session (and the clock Supabase reads for token expiry) is read only at request time, never during a prerender or prefetch (AD-027). A user with several memberships acts for the earliest one. Adapters: [web/infrastructure/supabase/auth.ts](web/infrastructure/supabase/auth.ts).
  - **The `(app)` gate:** [web/app/(app)/layout.tsx](web/app/(app)/layout.tsx) renders `MemberGate` inside `<Suspense>` (Cache Components cannot prerender a session read). Signed out redirects to `/login`; no membership shows "No workspace yet" with Sign out; a member gets the shell with the org name, their email and Sign out (scope `local`, this browser only).
  - **Members page** ([.specs/features/members-page/](.specs/features/members-page/)): `/members` ([page](web/app/(app)/members/page.tsx), [view](web/components/members/members-view.tsx)) lists the org's members for every role, and for owners and admins the pending invitations and the controls: invite by email with a role (default Viewer), Resend, Revoke, change role, Remove after a confirm. Everything is written by definer functions in migration `20261105120000_members_page` (no service-role key): `create_invitation`, `revoke_invitation`, `set_member_role`, `remove_member`, `accept_invitations`, and the reads `list_members` and `list_invitations` (emails come from `auth.users`). `public.invitations` holds the offers (14 days, one live row per address and org). Only an owner can grant, change or remove an owner; the last owner stays (`last_owner`, then `self`); acting on yourself is refused. `memberships` has no write privilege for `authenticated` any more.
  - **Inviting needs no service-role key:** the invite action stores the invitation, then asks Supabase Auth for a link with `signInWithOtp({ shouldCreateUser: true })` from a cookie-less client ([members.ts](web/infrastructure/supabase/members.ts)). The Before User Created hook `private.hook_before_user_created` lets Auth create a login only for an address with a live invitation (HTTP 403 "Sign-ups are by invitation." otherwise). `/auth/confirm` then calls `accept_invitations`, which turns the earliest live invitation into a membership when the person has none. `/login` still never creates accounts.
  - **Supabase config outside the repo (members page):** Authentication > Sign In / Providers: sign-ups enabled; Authentication > Hooks: Before User Created = `private.hook_before_user_created`; the **Confirm signup** email template link must be `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`, as the Magic link one is (a new address gets the Confirm signup email, confirmed live 2026-11-05: the first invite created the login and Auth tried to send that email).
  - **Supabase Auth's SMTP sender must be on the verified Resend domain** (Authentication > Emails > SMTP Settings, a sender address at `felipeviana.com`). While it is not, Resend answers 550 "You can only send testing emails to your own email address" and `signInWithOtp` returns 500 `unexpected_failure`: the owner's own sign-in links work, an invitation to anyone else is saved but its email is not sent (the page shows "The invitation was saved, but the email could not be sent. Use Resend.").
  - **Members before onboarding:** invite the user in the Supabase dashboard, then run [supabase/seed.sql](supabase/seed.sql) after `select set_config('app.demo_owner_email', '<email>', false);` to make them owner of the demo org. The address is never committed.
- **Not yet:** org creation is done by the service role only (onboarding is Phase 5). No org switcher, so a person who already belongs to an org cannot accept an invitation to another; no audit log of role changes.
- **Tests:** [supabase/tests/](supabase/tests/), run with `npm run test:db` (see "How to run the tests"); each run rolls back. Spec: [.specs/features/supabase-init/](.specs/features/supabase-init/).

### Company profile and default terms (M2)
**What it is:** each tenant's branding and contract defaults. Branding is legal name, address, phone, logo and accent colour. Default terms are repair discount %, CPI cap %, cancellation notice days, payment days, governing province and tax note (GST/PST/HST). Branding is data, not code: no company name is hard-coded, and seed or demo data uses a fictitious company.
**What we built:** table `org_settings`, one row per org (primary key `org_id`). Percent terms are `numeric(5,2)` between 0 and 100. `accent_color` is `#rrggbb`. `logo_path` is the key of the org's logo in the public Storage bucket `logos` (`<org id>/<uuid>.png` or `.jpg`, 1 MB), set from `/setup` and `/settings` by an owner or admin and drawn on the agreement and contract PDFs, the review page and the signing page (tenant-logo, AD-180, migration `20261111100000`, applied 2026-11-11).
- **Settings screen:** `/settings` ([web/app/(app)/settings/](web/app/(app)/settings/)) shows the legal name, address, phone, accent colour and the default terms. Owners and admins edit and save; estimators and viewers see it read-only. `saveSettingsAction` validates with `validateOrgSettings` ([web/domain/org-settings/index.ts](web/domain/org-settings/index.ts)), then `OrgSettingsStore.save` updates the row under RLS (an empty result means `forbidden`). The province is stored as a two-letter code (AD-025). Last write wins. The form uses the new `Select` ([web/components/ui/select.tsx](web/components/ui/select.tsx)).
- **Renewal settings (term-dates):** `org_settings.default_term_months` (1-60, default 12), `renewal_notice_days` (0-365, default 30) and `cpi_renegotiation_threshold_pct` (0-100, default 5), all `not null`. `/settings` shows them under "Renewal"; owners and admins edit them, others see them read-only. A new agreement's version 1 takes the default term months. A sent version freezes the notice days and the threshold into `snapshot.terms` beside the six default terms (AD-088 to AD-094). The next roadmap item (auto-renewal, W7) reads them. Spec: [.specs/features/term-dates/](.specs/features/term-dates/).
- **Renewal CPI (renewal):** `org_settings.renewal_cpi_pct` (-20 to 100, two decimals) and `renewal_cpi_as_of` (a date), both set or both null. `/settings` shows them as "CPI for renewals" and "As of" under Renewal; estimators and viewers read them as text. W7 uses them: unset, or older than 13 months, means every due agreement goes to a renewal draft (AD-096).
- **Proposal validity (proposal-expiry):** `org_settings.proposal_validity_days` (1 to 365, default 30), shown on `/settings` as "Proposals valid for (days)" under Default terms; estimators and viewers read it only. Send uses it to date each proposal (AD-104).
- **Demo org:** [supabase/seed.sql](supabase/seed.sql) creates the fictitious tenant `Kettle Ridge Mechanical Ltd.`, with fixed id `00000000-0000-4000-8000-00000000de30`. Its address is `100 Sample Street, Burnaby, BC`, its phone `604-555-0100` (the 555-01xx fiction range) and its accent `#1f6f8b`. Its default terms are 10 % repair discount (a placeholder, since the source template leaves it blank), 5 % CPI cap, 30 days' notice, payment in 30 days and BC. It has 12 agreements (one per site, version 1, mirroring the twelve mock cards; 3 contracts) and no events yet; its owner is attached with `app.demo_owner_email` (see Tenant). The seed has run once on the live project; re-running it changes nothing.

### Customer (M3)
**What it is:** the client company that owns the equipment and receives the service agreement, for example a property-management firm.
**What we built:** table `customers` (per org). The demo org has 12 customers, each with one contact (`@example.com` email) and one site.
- **Screens:** `/customers` lists customers by name with the primary contact (the earliest-created contact), site count and asset count, and a search. `/customers/[customerId]` shows contacts, sites and the customer's agreements; each agreement row links to `/agreements/[agreementId]`. Code: [web/components/customers/](web/components/customers/).
- **Forms (record-forms):** owners, admins and estimators get "New customer" on `/customers`, and "Edit", "Add contact" and "Add site" on a customer. Create pages nest under the parent (`/customers/new`, `/customers/[id]/contacts/new`, `/customers/[id]/sites/new`); edit pages are flat (`/customers/[id]/edit`, `/contacts/[id]/edit`) (AD-028). Viewers see no write controls, and a form route shows them "Only owners, admins and estimators can change customer records." Each form posts to a Server Action in [web/app/(app)/record-actions.ts](web/app/(app)/record-actions.ts): it refuses viewers, validates with [web/domain/records](web/domain/records/index.ts), then writes through a per-entity store port ([web/infrastructure/supabase/records.ts](web/infrastructure/supabase/records.ts), AD-029) and redirects to the record. Customers cannot be deleted. Field bounds: names 1-120, addresses 300, phone 40. Last write wins. Spec: [.specs/features/record-forms/](.specs/features/record-forms/).
- **Deactivation (deactivation):** customers, sites and assets are deactivated, never deleted. `deactivated_at` / `deactivated_by` (both set or both null) mark an inactive row; members may update only the columns the forms edit, so these are written only by `set_customer_active`, `set_site_active` and `set_asset_active` (security definer, owner/admin/estimator, `P0002` for another org; AD-112 to AD-116). The customer edit page has "Deactivate customer" (confirm step) and, once inactive, "Reactivate". Deactivating a customer deactivates every active site of theirs in the same transaction; reactivating brings back the customer only. `/customers` and a customer's Sites list hide inactive rows unless `?show=inactive` ("Show inactive" / "Hide inactive"), show an "Inactive" pill, and count active sites and assets only. An inactive customer offers no "Add site". Spec: [.specs/features/deactivation/](.specs/features/deactivation/).

### Contact / site contact (M3)
**What it is:** the person at the customer, usually a facility or property manager, who reviews the agreement through the portal and signs the contract. Their email approval counts as written approval. They are non-technical and use the portal rarely.
**What we built:** table `contacts`, belonging to a customer. A site's `site_contact_id` must name a contact of that site's customer, enforced by the composite FK `(site_contact_id, customer_id)`.
- **Forms:** add and edit contacts (name, optional email and phone). A contact can be deleted from its edit page after a confirm prompt; a contact that is some site's contact is refused (FK `23503`, AD-030).

- **Roles (contact-roles):** a contact can also be a site's **approver** (`sites.approver_contact_id`) or its customer's **billing contact** (`customers.billing_contact_id`), both composite FKs to a contact of the same customer ([supabase/migrations/20261104203234_contact_roles.sql](supabase/migrations/20261104203234_contact_roles.sql)). Customer emails (link, reminder, renewal notice) go to `private.customer_recipient(site)`: the approver's email, else the site contact's, else `no_recipient`. The expiry notice goes to staff and is unchanged. The customer page labels each contact `Billing`, `Approver · <site>`, `Site · <site>`; the site page shows `Approver: <name>`; the site form has an Approver select and the customer edit form a Billing contact select (none on New customer). Deleting a role holder is refused (`23503`). Billing is recorded only until Phase 6 invoicing. PostgREST embeds of a customer's contacts must name `contacts!contacts_customer_id_org_id_fkey`, because two FKs now join the tables.

### Site (M3)
**What it is:** a physical address belonging to a customer, where the equipment is installed. A customer can have several sites.
**What we built:** table `sites`, belonging to a customer, with an optional site contact. A site that has an agreement cannot be deleted.
- **Screen:** `/sites/[siteId]` ([web/app/(app)/sites/[siteId]/](web/app/(app)/sites/[siteId]/)) is the equipment register: assets grouped by asset type (ordered by type name, rows by unit with numbers compared as numbers), a search, and a link back to the customer. Writers get "Edit site", "Add asset" and per-asset "Edit".
- **Sites list (sites-page):** `/sites` ([web/app/(app)/sites/page.tsx](web/app/(app)/sites/page.tsx)) lists every site across customers, ordered by customer then site name: address, customer, active asset count, up to three equipment types as `RTU ×3` plus `+n more`, and the site's live agreement (`AG-n` and status pill) or "No live agreement". `?q=` (site, address or customer name), `?customer=<uuid>` and `?show=inactive` (shows inactive sites and sites of inactive customers with an Inactive pill) narrow it; the sidebar "Sites & equipment" item links here. Read through `SiteDirectory.list(filter)` ([web/infrastructure/supabase/readers.ts](web/infrastructure/supabase/readers.ts)); no migration (AD-122).
- **Imports history (imports-page):** `/imports` ([web/app/(app)/imports/page.tsx](web/app/(app)/imports/page.tsx)) lists every import job across sites, newest first: file, status pill, size, uploader, date, outcome line, site and customer links, and "Review rows" (extracted, committed) or "Open on site" (the rest). It is read-only: read, extract and discard stay on the site import page. `?status=` (one status or `attention`) and `?site=<uuid>` narrow it; the sidebar "Imports" item links here and is current on `/imports/*`. Read through `ImportHistory.list(filter)` ([web/infrastructure/supabase/imports.ts](web/infrastructure/supabase/imports.ts)); no migration (AD-123).
- **Global search (global-search):** `/search?q=<text>` ([web/app/(app)/search/page.tsx](web/app/(app)/search/page.tsx)) lists, in three groups (Customers, Sites, Equipment), the active customers whose name, sites whose name or address and units whose unit number contain the text (plain, case-insensitive substring; at most 25 per group, then "Refine your search"). Deactivated records and records under a deactivated parent are not searched. Read through `RecordSearch` and `public.search_records(p_query, p_limit)` (security invoker, so RLS decides the tenant; migration [supabase/migrations/20261105210000_global_search.sql](supabase/migrations/20261105210000_global_search.sql), AD-132). Reached from the sidebar field (desktop) and the top-bar Search link (below 1024px); every role may search.
- **Agreement on the site (agreement-builder):** a site has at most one **live** agreement (`draft`, `sent` or `changes_requested`). While it has one, every member sees a link `<number> · <stage label>` to it; while it has none, writers get "New agreement", which creates one and opens it. `SiteView.liveAgreement` comes from `SiteRegister` ([web/infrastructure/supabase/readers.ts](web/infrastructure/supabase/readers.ts)).
- **Forms:** add a site to a customer (`/customers/[id]/sites/new`) and edit it (`/sites/[id]/edit`): name, address and a site contact chosen only from that customer's contacts. The customer never changes. Sites cannot be deleted (agreements hang off them).
- **Deactivating a site (deactivation):** "Deactivate site" on the edit page asks `Deactivate <site>?` and names what it withdraws (`This withdraws AG-1004.`). In one transaction it withdraws the site's `draft` or `sent` agreement through `apply_agreement_transition` (event payload `{from, to: "withdrawn", via: "deactivation"}`, one outbox row) and stamps the site. It is refused while the site is **in term**: an `accepted` agreement whose latest `term_end` is today or later in America/Vancouver, or has none, or has a contract pending, client-signed or completed ("AG-1004 is in term until Dec 31, 2027, so this site can't be deactivated yet."); and while an agreement is `changes_requested` ("Revise and withdraw it first."). There is no cancellation yet (Phase 6). An inactive site shows "Inactive", offers no "New agreement", "Add asset" or "Import equipment list", `create_agreement` refuses it (`55000` / `site_inactive`) and W7 renews nothing on it. Reactivating a site under an inactive customer says "Reactivate <customer> first." Agreements withdrawn by a deactivation stay withdrawn.

### Asset and asset type (M4)
**What it is:** one piece of equipment at a site. Fields: asset type, unit #, type/model, location/access, and source (manual or import). The asset type comes from a catalog of about 40 equipment types, for example RTU (rooftop unit) and MUA (make-up air unit).
**What we built:** tables `asset_types` (catalog per org, `unique (org_id, code)`) and `assets` (per site, `source` is `manual` or `import`).
- **Codes:** an asset type code must match `^[A-Z][A-Z0-9_]*$`, for example `RTU`, `MUA` or `HWT_HIGH_EFFICIENCY` (check `asset_types_code_format`). Phase 2 synonyms map onto these codes.
- **Demo assets:** 57 assets across the 12 demo sites, using 27 of the 40 types, all `source = 'manual'`.
- **Default visit months:** each type has `asset_types.default_visit_months` (catalog: air-side and refrigeration quarterly, hydronic auxiliaries Apr and Oct, heating plant and annual tests October; AD-082). They prefill a new service line's month grid.
- **Forms:** `/sites/[id]/assets/new` and `/assets/[id]/edit`: equipment type (the org's `asset_types`, shown as `Name (CODE)`), unit #, type/model, location/access. New assets get `source = 'manual'`; an edit keeps `source`. With an empty catalog the add page says "Your equipment catalog is empty."
- **Removing an asset (deactivation):** assets are no longer deleted (AD-030 superseded for assets; `delete` is revoked from members). "Remove from service" on the edit page asks `Remove <CODE unit> from service?` and offers "Replaced by" (None, or another active unit of the same site, as `<CODE> <unit>`). The link is `assets.replaced_by_asset_id`, a composite FK to `(id, site_id)` so it cannot leave the site, set only on an inactive asset. The register hides removed assets unless `?show=inactive`, where they read `Removed` or `Removed · replaced by RTU-2`. `site_service_scope` leaves removed units out of the next draft; frozen snapshots keep them. "Reactivate" clears the link; on an inactive site it says "Reactivate <site> first."

### Asset import (M5)
**What it is:** turning a customer's messy equipment list (xlsx, csv, docx or pdf) into assets. The steps are upload, parse by format, extract with Claude structured output, normalize types with a synonym table (for example "Rooftop unit" → RTU), review in a grid, then commit. Uncertain rows are flagged, never hidden. Extraction sits behind the `AssetExtractor` port.
**What we built (step 1, upload):** spec [.specs/features/import-upload/](.specs/features/import-upload/).
- **Import job:** table `import_jobs`, one uploaded file for one site (`site_id` composite FK), status `uploading` -> `uploaded`, with original name, size, canonical content type, `created_by` and `created_by_email` from the JWT. RLS as `assets`: members read, owner/admin/estimator write (AD-031). Migration [supabase/migrations/20261026200326_import_upload.sql](supabase/migrations/20261026200326_import_upload.sql).
- **Storage:** private bucket `imports`, 20 MB, pdf/csv/xlsx/docx only (AD-032). Key `<org_id>/<job_id>`; a file can only be inserted for a job of that org still `uploading`; no overwrite; the first `storage.objects` policies in the project (AD-033). Direct SQL deletes on `storage.objects` need `set_config('storage.allow_delete_query','true', true)` (Supabase's `protect_delete` trigger).
- **Screen:** `/sites/[siteId]/import` ([web/app/(app)/sites/[siteId]/import/](web/app/(app)/sites/[siteId]/import/)), linked from the site register as "Import equipment list" for writers. Writers pick one file and press Upload; everyone sees the site's jobs newest first (name, size, uploader, date, "Uploaded" / "Upload not finished"); writers can Discard after a confirm prompt.
- **Upload path (AD-034):** `startImportAction` validates with `validateImportFile` ([web/domain/imports](web/domain/imports/index.ts)) and calls `ImportJobStore.start`, which inserts the job and signs an upload URL; the browser `PUT`s the bytes straight to Storage ([web/components/imports/state.ts](web/components/imports/state.ts) `uploadFile`); `confirmImportAction` checks the stored size and marks the job uploaded. Adapter: [web/infrastructure/supabase/imports.ts](web/infrastructure/supabase/imports.ts).
**What we built (step 2, read):** spec [.specs/features/import-parse/](.specs/features/import-parse/).
- **Read:** right after an upload is confirmed, `readImportAction` reads the stored file once and records the outcome on the job: `uploaded` -> `parsed` ("Read", with "48 rows in 1 table", "Text only, no table" or "PDF, read at extraction") or `unreadable` ("Can't read", with one of five reasons and its advice). A job whose read did not finish stays "Uploaded" with a "Read file" button. Migration [supabase/migrations/20261026220638_import_parse.sql](supabase/migrations/20261026220638_import_parse.sql) (AD-035).
- **Parsers:** `ImportParser` in [web/infrastructure/import-parsers/](web/infrastructure/import-parsers/) (AD-036). Spreadsheets and CSV through SheetJS 0.20.3 (installed from the SheetJS CDN tarball, because npm's `xlsx@0.18.5` has two high advisories): the header is the first row in a sheet's first 20 rows with at least 2 text cells (no numbers or dates) and a data row below; hidden sheets are skipped; CSV delimiters `,` `;` and tab are detected, and a CSV that is not UTF-8 is decoded as Windows-1252 (Excel's "CSV" on Windows). Word through `mammoth` (top-level tables with 2+ columns, plus the raw text). PDFs are only checked for `%PDF-` and passed on whole: Claude reads them in step 3. More than 2,000 data rows is refused. Password-protected Office files are recognised by their OLE signature.
- **Output for step 3:** `ParsedImport` is tables (header, rows with refs like `Units!4` or `Table 2, row 1`) plus document text, or the PDF bytes. It is not stored; extraction parses again.
- **Reads as the member:** `ImportJobStore.fileOf` downloads under RLS, never with a service-role key, and `recordRead` writes only while the job is `uploaded`, so two reads write once (AD-037).
- **Not yet:** download or preview of the file; cleanup of jobs left "Upload not finished".
**What we built (step 3, extract):** spec [.specs/features/import-extract/](.specs/features/import-extract/).
- **Flow:** on a "Read" job a writer presses "Extract equipment". The browser calls `extractImportAction` once per chunk (up to 100 data rows of one table, or the whole text of a table-less Word file, or a whole PDF) until the job is `extracted`. Each chunk: `ImportJobStore.sourceOf` (file bytes as the member, only while `parsed` / `extracting`) -> `ImportParser` re-parses -> `AssetExtractor` (Claude, structured output) -> `matchAssetType` -> `record_extraction_chunk` (AD-038 to AD-044). A closed tab leaves the job `extracting` with a "Continue extraction" button; a stale call stores nothing twice.
- **Claude:** [web/infrastructure/claude/](web/infrastructure/claude/) calls `claude-opus-5-5` (effort low, `json_schema` output, server-side refusal fallback). Only the chunk is sent: no org, customer, site or member identity. A refusal, bad answer or API error is `unavailable` ("We couldn't read this list. Try again."); a text or PDF answer that hits the output limit is `too_large`. `ANTHROPIC_API_KEY` is server-side only ([web/.env.example](web/.env.example)).
- **Matching:** `matchAssetType` in [web/domain/imports/index.ts](web/domain/imports/index.ts) compares code or name (lowercased, punctuation collapsed), then the spellings the org's own types hold (`asset_types.synonyms`, e.g. "Rooftop unit" on RTU, "MAU" on MUA; synonyms-as-data, AD-160); no match or more than one gives no type, and the row is stored with `asset_type_id` null and counted as needing a type.

### Service agreement (M7, M8)

- Visit frequency: the months each line's visits fall in ("visit months"); visits per year is their number.
- Service price lines (visits per year × cost per visit), each covering one or more equipment types.
- A visit schedule: which equipment is serviced in which month. Money is stored in integer cents, in CAD.
- "Service included", built from the asset types on site and their checklists.

### Pipeline / status engine (M11)
**What it is:** a pure state machine for agreements and contracts. Every transition writes an event and an outbox row. Each deal is shown at one stage: **In progress → Sent to customer → Accepted (awaiting signature) → Completed**, with **Refused** as the exit. The dashboard shows deals by stage and age.
**What we built:**
- **Domain layer:** pure TypeScript in [web/domain/](web/domain/), with no framework, database or UI imports. An ESLint `no-restricted-imports` rule on `domain/**` enforces this (AD-010). Spec: [.specs/features/domain-layer/](.specs/features/domain-layer/).
  - **Agreement machine:** `applyAgreementCommand(status, command)` in [web/domain/agreement/index.ts](web/domain/agreement/index.ts). It allows 8 moves: `send` (draft→sent), `accept`, `refuse`, `request_changes` and `expire` (all from sent), `revise` (changes_requested→draft, new version `n + 1`), and `withdraw` (from draft or sent). `refuse` and `request_changes` need a reason of 1–2000 characters after trimming.
  - **Contract machine:** `applyContractCommand(status, command)` in [web/domain/contract/index.ts](web/domain/contract/index.ts). `client_sign` (pending_signature→client_signed) and then `countersign` (→completed); `decline` and `void` work from either open status.
  - **Result:** a refused move returns `{ ok: false, error: { code, from, command } }` with code `invalid_transition`, `reason_required` or `reason_too_long`; it never throws. A successful move returns `{ ok: true, status, event }`. The event's type is `<entity>.<to-status>` (`agreement.sent`, `agreement.revised`, `contract.completed`...). It carries `from`, `to` and `data` (`reason` or `versionNo`) (AD-011). The transition use cases below record it.
  - **Stage:** `pipelineStage(agreement, contract?)` in [web/domain/pipeline/index.ts](web/domain/pipeline/index.ts). draft and changes_requested → In progress; sent → Sent; accepted → Accepted until the contract completes (→ Completed). Customer-side endings (refused, expired, contract declined) → Refused. Contractor-side endings (withdrawn, contract voided) → `null`, off the board.
- **Stage keys:** `in_progress`, `sent`, `accepted`, `completed` and `refused` are owned by [web/domain/pipeline/index.ts](web/domain/pipeline/index.ts) (AD-001). [web/lib/pipeline-stage.ts](web/lib/pipeline-stage.ts) re-exports them and keeps only the UI labels and dot classes.
- **Board UI:** `/pipeline` ([web/app/(app)/pipeline/page.tsx](web/app/(app)/pipeline/page.tsx)) shows the five-column board on the member's agreements.
  - Each column shows its card count and its CAD total per year, formatted by `formatCad` from [web/lib/money.ts](web/lib/money.ts).
  - Search by customer name runs client-side.
  - On mobile the board becomes stage tabs; on tablet it scrolls inside its own container.
- **Redirect:** `/` redirects to `/pipeline` with a 307 ([web/next.config.ts](web/next.config.ts)).
- **Recording a transition:** server code calls `getContainer()` from [web/composition/index.ts](web/composition/index.ts) (`server-only`, one per request, built from the request cookies) and then `transitionAgreement({ agreementId, command })` or `transitionContract({ contractId, command })`. The use case ([web/application/use-cases/index.ts](web/application/use-cases/index.ts)) loads the record through a repository port ([web/application/ports/index.ts](web/application/ports/index.ts)), lets the domain machine decide, and commits. It returns `{ ok: true, status, eventId }`, a domain refusal, or `not_found`, `conflict` (someone changed it first) or `forbidden` (viewer). Unexpected database or network errors are thrown. `revise` reads the current version itself, so callers pass no version number.
  - **Adapters:** [web/infrastructure/supabase/index.ts](web/infrastructure/supabase/index.ts) calls the RPCs below and maps SQLSTATE `40001`, `P0002` and `42501` to those codes. [web/infrastructure/supabase/database.types.ts](web/infrastructure/supabase/database.types.ts) is generated with MCP `generate_typescript_types`; regenerate it after each migration.
  - **Clock:** the `Clock` port has `systemClock` and `fixedClock(d)` in [web/infrastructure/clock/index.ts](web/infrastructure/clock/index.ts). Nothing reads it yet; deal age will be its first reader.
  - **Layer rules:** ESLint keeps `application/` free of framework and database imports, keeps `infrastructure/` away from UI, and stops `app/`, `components/` and `lib/` importing adapters or `@supabase/*` (AD-014).
  - **Config:** `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `web/.env.local` (untracked); [web/.env.example](web/.env.example) lists them. A transition runs as the signed-in member.
  - Spec: [.specs/features/ports-adapters/](.specs/features/ports-adapters/).
- **Real data:** `/pipeline` reads the member's agreements through `PipelineReader` ([web/infrastructure/supabase/readers.ts](web/infrastructure/supabase/readers.ts)). A card shows the site as its heading, the customer beneath it, `<number> · v<n>`, the age (whole days since `agreements.updated_at`, via `Clock`) and the annual amount of the latest version's service lines. Withdrawn agreements and voided contracts are off the board. The sample data is gone. The board search matches the site or the customer name (trimmed, case-insensitive), and each column header counts and totals only the matching cards.
- **Card links:** each card opens `/agreements/[agreementId]` (agreement-builder). The board's "New agreement" button stays disabled; agreements start from a site.

### Events, outbox and n8n automation (M11, M12, M13)
**What it is:** the app owns all status, and n8n only automates emails, reminders and timing. Outbox events go to n8n signed with HMAC, and n8n calls back app endpoints with idempotency keys. n8n execution IDs are written back to the event log as audit evidence. Workflows W1–W6 are defined in [ROADMAP.md](ROADMAP.md#n8n-workflows). Customers never see or build workflows.
**What we built:** Phase 3 item 5 (spec [.specs/features/outbox-dispatch/](.specs/features/outbox-dispatch/)): the database dispatches the outbox and verifies n8n's callbacks itself; the app writes and sends the emails; n8n only routes and waits. No service-role key anywhere.
- **`events`:** append-only for app users. Members read and writers insert. `update` and `delete` are revoked from `anon` and `authenticated`. `n8n_execution_id` is written once, by `automation_claim`, the first time a callback names the event.
- **`outbox`:** `event_id unique`. Status `pending`, `sending`, `sent` (n8n answered 2xx) or `failed`, with `attempts`, `available_at`, `last_error`, `request_id` and `dispatched_at`. All privileges are revoked from `anon` and `authenticated`. The migration retired every row enqueued before dispatch existed (`failed`, `enqueued before dispatch existed`).
- **Write path:** `public.apply_agreement_transition` and `public.apply_contract_transition` in [supabase/migrations/20261023222239_transition_rpcs.sql](supabase/migrations/20261023222239_transition_rpcs.sql) update the status only if it still equals the expected one, insert the event (`actor_id = auth.uid()`, payload `{from, to, reason?, versionNo?}`), insert the next `agreement_versions` row on `agreement.revised` (copying the previous snapshot, not its service lines), and enqueue the outbox row, in one transaction. They run as the caller, so RLS applies, and only owner, admin and estimator may call them; `anon` cannot (AD-015, AD-017).
- **Outbox writer:** `private.enqueue_outbox(event_id)` (and `enqueue_outbox_for_system` for portal decisions) are the only writers. No trigger enqueues, so events such as `agreement.viewed` never reach n8n (AD-016, AD-069).
- **Dispatcher (outbox-dispatch, AD-073):** `pg_cron` job `outbox-dispatch` runs `private.dispatch_outbox()` every minute: it settles `sending` rows from `net._http_response` (2xx `sent`; anything else, or nothing after 10 minutes, back to `pending` at +1, 5, 15, 60, 240, 720, 1440 minutes, `failed` at attempt 8), then `pg_net` posts up to 50 due rows to the Vault `n8n_events_url`, signed with Vault `automation_hmac_secret`. Without either secret it does nothing (the live state today). Migration [supabase/migrations/20261029165430_outbox_dispatch.sql](supabase/migrations/20261029165430_outbox_dispatch.sql), proofs [supabase/tests/outbox_dispatch.sql](supabase/tests/outbox_dispatch.sql).
- **Signature (AD-074):** both directions send `X-SA-Timestamp` (unix seconds) and `X-SA-Signature: sha256=<hex HMAC-SHA256(secret, timestamp + "." + raw body)>`, accepted within 300 s.
- **Callbacks (AD-075):** n8n posts to `POST /api/automation/notify` ([route](web/app/api/automation/notify/route.ts)), public under the `PUBLIC_PREFIXES` entry `/api/automation/` (AD-072). The route refuses malformed headers with `401`, then the `notify` use case ([web/application/use-cases/notify.ts](web/application/use-cases/notify.ts)) calls `public.automation_claim` through an `anon` publishable-key client ([adapter](web/infrastructure/supabase/automation.ts), `getAutomationContainer` in [composition](web/composition/index.ts)): the database checks the signature, the body and the key, writes the execution id, claims the notification and returns each email's data. The app builds the email, sends it, and records the outcome with `public.automation_complete`. Answers: `200 {outcome: sent | skipped | duplicate}`, `400`, `401`, `404`, `409` (in flight), `503` (provider or database failure, or `email not configured`).
- **Notifications (AD-076):** `public.notifications`, one row per idempotency key (`w1:<eventId>:link|day3|day7`, `w3:<eventId>`, `w5:<date>:<orgId>`, `w7:<renewalId>:customer|staff`, `w8:<eventId>`), kinds `customer_link`, `customer_reminder`, `staff_decision`, `staff_stale`, `customer_renewal`, `staff_renewal`, `staff_expired`, status `claimed`, `sent`, `skipped` (with a reason) or `failed`. Members read their org's rows.
- **Emails ([web/domain/notifications](web/domain/notifications/index.ts)):** the customer link and its day-3 and day-7 reminders (tenant's name and accent, one "Review the agreement" button, site, yearly total before tax, phone, no product name; Reply-To the sending member), the estimator's refusal or change-request email (fallback: owners and admins), and the daily stale digest for owners and admins (sent agreements unviewed 7 days after sending). Reserved test domains (`example.com/.org/.net`, `.test`, `.invalid`) are skipped as `reserved_domain`.
- **Email provider (AD-078):** Resend, over `fetch` with `Idempotency-Key` ([web/infrastructure/email](web/infrastructure/email/index.ts), `EmailSender` port), sending from `EMAIL_FROM` on the Resend domain `felipeviana.com` as `"<tenant legal name>" <EMAIL_FROM>`. `RESEND_API_KEY`, `EMAIL_FROM` and `PORTAL_LINK_KEY` are server-only and read only in `composition/` ([.env.example](web/.env.example)).
- **Sealed link (AD-077):** Send and "Get a new link" also store the token sealed with `PORTAL_LINK_KEY` (AES-256-GCM, `PortalTokens.seal`/`unseal` in [web/infrastructure/portal-tokens.ts](web/infrastructure/portal-tokens.ts)) so a reminder can rebuild the live link; the database still cannot act as the customer.
- **n8n instance:** self-hosted on Railway, project `service-agreement-automation`: service `n8n` (image `n8nio/n8n:2.45.7`) with its own `Postgres` service. Editor and webhooks at `https://n8n-production-297b.up.railway.app/`, timezone `America/Vancouver`, env access in nodes left at n8n's default. Deployed 2026-10-30; the four workflows are imported and active (W1, W3, events, W5), with the placeholders replaced and the shared HMAC secret in Supabase Vault (`automation_hmac_secret`, `n8n_events_url`). The web app runs in the same project as service `web` at `https://web-production-bde48d.up.railway.app` (its `APP_BASE_URL`), so n8n's callbacks reach it. The URL was added to the Supabase Auth redirect list (confirmed by the owner 2026-11-04).
- **n8n workflows (AD-079, [automation/n8n/](automation/n8n/)):** `events.json` (webhook answers 200 on receipt, verifies the raw body with a Crypto node and the 300 s window, routes `agreement.sent` to W1 and `agreement.refused` / `agreement.changes_requested` to W3, ignores the rest), `W1-agreement-sent.json` (link now, wait 3 days, reminder, wait 4 days, reminder), `W3-agreement-decided.json`, `W5-stale-daily.json` (08:00 America/Vancouver). Each notify call is Set -> Crypto HMAC -> HTTP Request, so the bytes signed are the bytes sent. A `409`, `500`, `502`, `503`, `504` or network error loops through a 10-minute Wait back to the same Set node (same key, fresh timestamp and signature), at most 6 retries; then W1 moves on and W3, W5 end (C1052). n8n is self-hosted on Railway with Postgres (`DB_TYPE=postgresdb`, so waits survive a redeploy). The exports carry two placeholders, `__SA_HMAC_SECRET__` (the Crypto nodes' secret) and `__SA_APP_BASE_URL__` (the start of each notify URL), and no `$env` (plan Landing 13): replace the two placeholders in n8n after import. Also after import, pick W1 and W3 in the events workflow's two Execute Workflow nodes. Imported and active on the Railway n8n since 2026-10-30 (see n8n instance above).
- **W7 (renewal, AD-099, AD-100, AD-102):** `W7-renewal-daily.json` calls notify at 08:00 America/Vancouver with `renewal_daily` and key `w7:<yyyy-mm-dd>`. The claim runs the day's renewals, then returns one `customer_renewal` email per auto-renewal (to the site contact: new term, old and new annual totals, applied %) and one `staff_renewal` email per renewal draft (to owners and admins: the reason and a link), keyed `w7:<renewalId>:customer|staff`, so a failed send is retried by the next run. Imported into the live n8n instance and active since 2026-11-04.
- **W8 (proposal-expiry, AD-107, AD-108, AD-110):** `W8-expiry-daily.json` calls notify at 08:00 America/Vancouver with `expiry_daily` and key `w8:<yyyy-mm-dd>`. The claim expires every sent proposal past its date, then returns one `staff_expired` email per expiry ("AG-1004 expired without a decision": customer, site, the date and a link) to the member who sent it, else the owners and admins, keyed `w8:<eventId>`, so a failed send is retried by the next run. Imported into the live n8n instance and active since 2026-11-04.
